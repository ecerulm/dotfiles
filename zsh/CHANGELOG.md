# Changelog

All notable changes to the zsh configuration are documented here.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [2026-08-13]

### Added

- `rlm-gar-version-rm` (`gar-version-rm`): **delete individual versions inside one package**, where `gar-rm` deletes whole packages. Two pickers — the shared gar-\* package picker (single-select), then a TAB-multi-select list of the versions inside it, newest first, showing date, size, short digest and tags with untagged versions dimmed. The preview shows the image name, every tag on the digest, the full SHA, size, media type (flagging multi-arch indexes), upload/update/create/build times, platform, and any other scalar metadata, and warns when a digest carries several tags since deleting it removes all of them. The version list is fetched once and passed to the preview as a cached file — a per-version API call would make a preview that re-runs on every keystroke unusable.

- `rlm-gar-version-rm`: prints the exact gcloud command lines, confirms once for the whole selection, deletes in batches of ≤1000 digests, then **re-lists the package and checks each selected digest against what remains**, offering a single retry for any still present. Verified against a mock registry covering the normal path, selecting every version, and a delete that reports success while changing nothing — the last is the case a bare exit-code check would call success.

- `rlm-gar-version-rm`: selecting every version leaves an empty package behind (versions delete does not reap the package), which is called out before the confirmation with a pointer to `gar-rm` rather than silently leaving a shell in the picker.

- `bin/gar-version-preview`: per-version detail pane for the above.

### Changed

- **All `rlm-gar-*` commands now share one implementation.** The three user-facing commands are thin — preflight → pick → act — with everything else in helpers, so a change to the cache, picker chrome, or command rendering lands in all of them at once. New: `_rlm-gar-preflight` (env + tool validation), `_rlm-gar-pick-package` (the entire cache-backed package picker including the refresh sentinel and its project sub-picker), `_rlm-gar-history` (shared MRU, `append`/`remove`), `_rlm-gar-parse-image` (image-path split), `_rlm-gar-show-cmd` (command rendering); `_rlm-gar-cache` gains `remove`. `rlm-gar-open` 118 → 43 lines, `rlm-gar-rm` 392 → 275.

- `_rlm-gar-parse-image` splits **positionally** rather than with `cut -d/ -f4-`, so nested package paths (`app-engine-tmp/app/dbt-docs/ttl-18h`) survive intact. It also replaces a copy in `rlm-gar-open` that computed `repo_name` twice, the second time overwriting the first with the same value via a different method.

### Fixed

- `bin/gar-rm-preview`: **the preview crashed on Python 3.12+** — `f"{dt.strftime(\"%Y-%m-%d\")}"` uses escaped quotes inside an f-string, which is a `SyntaxError` here (`unexpected character after line continuation character`). Three occurrences; the expressions are now hoisted into locals. The bug shipped in the previous commit because the only live test hit an auth failure before reaching the Python block, so the crash was masked by the (correctly reported) credential error.

- `rlm-gar-version-rm`: a second bare `local d` in the same function printed `d=sha256:…` to **stdout** on every call — the documented zsh "bare `local` in a loop re-declares and reports" trap, caught because the leak appeared in the delete summary. All loop-body locals across the gar helpers now carry explicit initializers.

- `rlm-gar-rm`: the post-delete cache/history prune still referenced `$cache_file` and `$history_file`, which the shared-helper refactor had removed from scope — it would have silently pruned nothing. Now goes through `_rlm-gar-cache remove` and `_rlm-gar-history remove`, tracking the actually-deleted images rather than the originally-selected ones.

- `rlm-gar-rm` (`gar-rm`): **multi-select fzf picker over GAR `<repo>/<package>` entries that deletes them.** Reuses `gar-open`'s package list, cache, and MRU history rather than building its own — same `~/.cache/gar-open/<md5>.txt`, same key, same `--- REFRESH CACHE ---` partial-refresh picker — so a refresh in either command benefits the other and the two can never disagree about what exists.

- `rlm-gar-rm`: deletion runs in **two phases, because `gcloud artifacts packages delete` fails server-side above 1000 versions**. Versions go first in batches of ≤1000 via `versions delete --delete-tags`, re-counting between batches until none remain, then the empty package is removed. Confirmation is per package, not per batch: a 2500-version package is one keypress and three batches, not four prompts. After the batches, the package is re-queried to **verify** it is actually gone; if versions remain the count is reported and a retry offered. A batch that reports success without reducing the count aborts that package rather than spinning — the guard exists because "delete succeeded, nothing changed" is indistinguishable from progress if you only trust exit codes. Verified against a mock registry covering the 2500-version batching path and the stuck-delete path.

- `rlm-gar-rm`: the exact `gcloud` command lines are printed before the confirmation prompt, one argument per line. Digest lists render as `<N version digest(s)>` rather than expanding — 1000 sha256 digests would bury the `--project`/`--repository` flags that actually determine what gets destroyed. Packages needing more than two batches show the first two and a note that the rest are identical.

- `rlm-gar-rm`: `versions list --format='value(name)'` returns **fully qualified** resource paths, but `versions delete` wants the bare version id when `--package`/`--location`/`--repository` are given; ids are stripped to the last `/versions/` segment. Passing the qualified form is an `INVALID_ARGUMENT` that only appears against the real API, so the mock asserts against it.

- `bin/gar-rm-preview`: deletion-oriented preview — version count, total size, newest/oldest version dates, tag count, package create/update time and annotations, the number of 1000-version batches required, and a sample of the newest tagged versions. Distinct from `bin/gar-preview`, which is browse-oriented and lists the 10 newest tags.

- `bin/gar-rm-preview`: an auth or permission failure is reported **loudly** instead of being swallowed. The first draft discarded stderr from `docker images list` and rendered a failed call as `(no versions found)` — on a delete tool that reads as "this package is empty, safe to delete". Caught when an expired token and a missing `artifactregistry.packages.get` on prod both produced a reassuring empty preview. Exit status is now checked, stderr surfaced, and the pane says the version count is unknown.

### Changed

- `rlm-gar-open`: **288 → 118 lines.** The fetch, merge, cache-age, MRU-sort, and project-picker logic moved into the shared `_rlm-gar-cache` and `_rlm-gar-pick-projects` helpers so `gar-rm` reuses it instead of holding a second copy that would drift. The cache key is unchanged (md5 of the sorted, deduped project list), verified to match the previously inlined computation against the real `GAR_SEARCH_PROJECTS` — the existing 141-entry cache is reused, not orphaned.

## [2026-08-12]

### Added

- `rlm-git-status` (`git-status`, `git-repos`): **a `PUSH` column reporting divergence from the branch's own upstream — the "ahead 4" that `git status` prints.** The existing `AHEAD/BEHIND` column measures against `origin/<default>`, which answers "how much work is on this branch" and says nothing about whether that work exists anywhere but this laptop. The two readings diverge in exactly the situation worth catching: a feature branch reported `+8` vs `origin/main` while `git status` in the same worktree said `ahead 4`, i.e. four commits had never been pushed, and nothing in the table showed it. Both numbers were correct and neither was the one you needed. `PUSH` renders `^N` unpushed, `vN` unpulled, `^N vN` diverged, `unpushed` when the branch has no upstream at all, `gone` when its upstream ref was deleted, `-` on a detached HEAD, and `=` when pushed and in sync. Unpushed work is yellow (yours to fix), unpulled and gone are red (someone else moved, or the branch is orphaned).

- `rlm-git-status`: the column is **dropped entirely when every repo is pushed and in sync**, which is the steady state — a full column of `=` is the same noise the `JIRA` column is already suppressed for. A summary line below the table counts the work across the collection (`4 unpushed commits in 1 repo`), since unpushed commits are the one state here that is both easy to forget and cheap to fix; it is counted over every repo rather than the rendered ones, so `--changed` cannot hide it. `--changed` also now treats unpushed commits as a change, so a repo whose tree is clean and which matches the base but is sitting on unpushed work no longer collapses into the `unchanged:` line.

- `rlm-git-status`: `unpushed` and `gone` are reported **only for a branch that actually carries commits**. `rlm-pr-worktree`'s multi-repo mode sets an upstream on every member at creation time, so an untouched member sits at `[gone]` with nothing on it — the common case, not an anomaly. The first draft flagged those and turned a 7-repo collection into "7 of 7 repos with changes" with six spurious red `gone` cells, which defeats the entire point of `--changed`. Gating on `ahead > 0` vs the base leaves the meaningful case intact: a `gone` upstream on a branch that *does* have commits means the remote branch was deleted out from under real work. Verified against throwaway repos covering all six states (in sync, behind, diverged, gone-with-commits, no-upstream-with-commits, detached) rather than by inspection.

- `rlm-git-status`: state is read with a single `for-each-ref --format='%(upstream:short)%09%(upstream:track)'` per repo, inside the existing parallel fan-out (7 repos still complete in ~240ms). Both fields are needed because `%(upstream:track)` is empty for **two** different states — in sync and no-upstream-at-all — which are only distinguishable by whether `%(upstream:short)` is also empty; reading the track field alone silently reports an unpushed branch as in sync. The branch is interpolated as a full `refs/heads/<branch>` path so a branch named `HEAD` cannot be misresolved.

- `rlm-pr-worktree-rm-merged-closed`: **per-phase progress on stderr**, because the scan is network-bound and spent tens of seconds with nothing on screen. Each phase names the repo it is on (`[3/7] scanning data-platform-dbt…`), and the deletion loop names the worktree in flight, since a single removal is several seconds of silent `unlink()`. Output is rewritten in place with `\r` on a TTY and falls back to plain lines when redirected; `PRWTRMC_QUIET` silences it. It must go to **stderr**: the picker rows are assembled on stdout and piped into fzf, so a progress line there becomes a bogus selectable row.

### Changed

- `rlm-pr-worktree-rm-merged-closed`: **PR state is resolved with one targeted `gh pr list --search "head:a head:b …"` per repo instead of paging the last 500 PRs** — 55.5s → ~21s across 7 repos, with the deletable set and the remaining-worktrees table verified byte-identical to the old output. The bulk fetch was also **wrong** on a busy repo: `--limit 500` only reached back to PR #3271 on `data-platform-dbt`, so any worktree whose PR predated that window missed the map, fell through to a per-branch `gh` call, and was silently labelled "no PR" whenever that fallback was skipped. Asking only about the branches the repo actually has worktrees for is both cheaper and complete regardless of PR age.

- `rlm-pr-worktree-rm-merged-closed`: `head:` in a search is a **prefix** match, not an exact one — `head:DATA-2792` also returns `DATA-2792/feat/partition_config` — so results are filtered to exact `headRefName` hits. Without that a worktree inherits a sibling branch's PR state, and a merged sibling would mark it deletable. Where several PRs share a head branch the highest number wins, matching what `gh pr view <branch>` reports. Terms are batched at 40; no ceiling appeared at 60 terms / 2.6KB, but a silently truncated query would mislabel real PRs as "no PR", which is the one failure this map must not have.

- `rlm-pr-worktree-rm-merged-closed`: the per-branch fallback is now a single `gh pr view` (an object, so `.state`, not `.[0].state`) and runs **only for branches with an `origin/<branch>` ref** — an unpushed branch cannot have a PR, and that round trip previously ran for 6 of 19 branches in `data-platform-dbt` only ever to come back empty.

- `rlm-pr-worktree-rm-merged-closed`: deletion stays **serial**, now with a comment recording why so it does not get "optimised" again. Removal is dominated by `unlink()` — a worktree's `.venv` is 518MB / 18,352 files, 89% of its 581MB — and parallelising buys nothing: 7 worktrees × 6k files measured 8.71s serial vs 8.74s parallel, and with git removed from the picture entirely `rm -rf` gave 8.705s vs 8.743s. APFS serialises the metadata mutations, so background jobs queue on the same lock and only the CPU accounting changes (system time 0.39s → 5.13s at identical wall clock). Concurrency is *safe* — 8 simultaneous removes against one repo all exit 0, git locks `.git/worktrees/` itself — it is simply not faster. Batching is not available either: `git worktree remove` takes exactly one worktree per invocation.

### Fixed

- `rlm-pr-worktree-rm-merged-closed` (`pr-worktree-rm-merged-closed`): **collection aggregate rows list their member states in a fixed canonical order** — `merged, closed, no-pr/no-diff, open, has-work, detached` — instead of first-seen order. The summary was built by walking members and appending each state the first time it appeared, so the order depended on which repo happened to be iterated first: the same collection rendered `[7 wt: 6 no-pr/no-diff, 1 merged]` on one run and `[7 wt: 1 merged, 6 no-pr/no-diff]` on the next, and two collections with identical state mixes could disagree with each other in a single picker. That defeats the point of the flag, which is read by eye across a stack of rows. Deletable states are listed first so the leading count is the one that answers "can I drop this". Unknown states (a future flag) are appended after the known set, sorted, so nothing is silently dropped from the summary.

## [2026-08-10]

### Added

- `rlm-git-update` (`git-update`): **the write counterpart to `rlm-git-status` — switch every repo in a collection dir to the target branch and hard-reset it to `origin/<branch>`.** Converted from an `update-all-repos.sh` script that did `cd "$(dirname "$0")"` and globbed `*/`, so it only ever worked on the one directory it happened to live in and had to be copied into each new collection. It now takes an optional `[<directory>]` defaulting to cwd and reuses `rlm-git-status`'s discovery rule verbatim: immediate children that are their own worktree root, falling back to the enclosing repo when there are none, so the read view and the write action cover the same set from anywhere. Discovery must test `git rev-parse --show-toplevel` **and** compare it to the directory itself — the first draft tested `--git-dir`, which answers from any depth inside a repo, so running it inside `data-platform-dbt` reported the plain subdirectory `dbt_docs_viewer` as a separate repo and would have reset it. Same trap `rlm-git-status` documents hitting.

- `rlm-git-update`: the destructive parts are fenced, because treating a branch as a read-only mirror of the remote means unpushed commits on it are destroyed. Repos with uncommitted changes to *tracked* files are skipped and listed — untracked files do not block, since `reset` leaves them alone, and blocking on them would make the function unusable in a tree with build output. Commits present locally but not on origin are listed before being discarded and stay recoverable via `git reflog`; stashes (`refs/stash`) and other branches are never touched; a branch left behind with no upstream is reported so local-only work stays visible. Each repo is fetched with `--prune` **before** the reset — resetting to a stale cached `origin/<branch>` reports success while pinning the repo to an old commit, which is the failure mode that looks most like it worked. Verified against throwaway repos rather than by inspection: a dirty tracked file survived the run, and a discarded commit was confirmed still in the reflog.

- `rlm-git-update`: flags are `-n`/`--dry-run` and `-b`/`--branch <name>` (long forms added to match the neighbouring functions; the script had bare `getopts` short flags). `-h` prints a usage line instead of the script's trick of `sed`-ing its own header comments out of `$0`, which has no meaning for an autoloaded function — that prose moved to `helpdir/`. Exit codes are preserved: 0 clean, 1 any repo failed, 2 bad usage. Colors only when stdout is a tty, so the log stays pasteable.

### Changed

- `.zshrc`: zoxide's interactive picker (`zi`) is configured via `_ZO_FZF_OPTS`, bringing it in line with the fzf conventions the `rlm-*` pickers follow — `--no-mouse` (so the terminal keeps selection/copy and OSC 8 links stay clickable), `--ansi`, and `ctrl-g:abort` as the escape hatch Ghostty's keyboard protocol can otherwise swallow. The variable is exported *before* `zoxide init zsh` is evaluated, and it replaces zoxide's built-in option set rather than adding to it, so the upstream defaults (`--no-sort --keep-right --cycle --exit-0`, the `ls` preview, the `btab`/`tab` navigation binds) are restated alongside the additions.

- `rlm-git-status` (`git-status`, `git-repos`): **absorbed the in-progress `rlm-git-repos` inventory view; the two are now one function and `rlm-git-repos`/`git-repos` are aliases.** They had been written as complements — one the verbose local-work view, one the one-row-per-repo inventory with PR and JIRA columns — but the split did not survive contact with use: both scanned the same directory the same way, resolved the same base ref, computed divergence with the same `rev-list --left-right --count`, and rendered the same padded-against-visible-width divergence cell, so ~150 lines were duplicated and every fix had to be applied twice. The question they answered was also one question, not two: "where does this change set stand" spans uncommitted work *and* whether it has been pushed, and having to run two commands to see both halves is what made the split feel wrong. The merged table carries all four state columns (`AHEAD/BEHIND`, `LOCAL`, `PR`, `JIRA`), which stay independent rather than collapsing into a "differs" boolean — a repo can be committed with no PR, or have a PR open while its tree is still dirty, and those are different situations.

- `rlm-git-status`: **every repo now gets a row by default; the `unchanged:` roll-up moved behind `--changed`.** The pre-merge default listed only dirty-or-diverged repos, which is right when you are asking "what is left to do" and wrong when you are asking "what does this change set look like" — the inventory reading needs the clean rows present. `-a`/`--all` is accepted as a no-op so the old spelling still works. The header hoists `BRANCH` and `JIRA` out of the table when every repo shares one value (as collection members do) and drops those columns, which is what keeps a 6-column table inside 80 columns; the `JIRA` column is also dropped when *no* repo resolved a key, since a column of `-` is noise. Hoisting is computed over all rows rather than the rendered ones, so `--changed` does not shift columns in and out depending on which repos happen to be dirty.

- `rlm-git-status`: PR and JIRA lookups are on by default, with `-P`/`--no-pr` and `-J`/`--no-jira` to skip. The `gh pr list` call is the slow part (~300-800ms/repo), so it rides the existing background fan-out — 7 repos land in ~700ms rather than ~4s. `--no-pr` is also implied when `gh` or `jq` is missing. JIRA summaries reuse the `~/.cache/wts-jira/<KEY>.summary` cache shared with `wt-preview`/`wt-collection-preview` on the same 3-day TTL, refreshed once per key rather than once per repo since collection members share one.

- `rlm-git-status`: the divergence column keeps the `AHEAD/BEHIND` label rather than the pre-merge `VS <base>`; the base ref it is measured against is still reported, but per-row only when a repo's base differs from the majority. Column width is derived from the label rather than hardcoded, so header and per-row padding cannot drift apart if it is reworded.

- `rlm-git-status`: the "N with a PR" summary counts over **all** members, not just the rendered rows. Under `--changed` a clean, in-sync repo can still have a merged PR, and counting only rendered rows would have under-reported against a total that is stated in full-member terms.

### Added

- `rlm-bq-archive` (`bq-archive`): **the confirmation step now shows what you are about to archive, not just which tables.** Previously the prompt listed bare FQNs, so the row counts and sizes needed to judge the decision were only available by scrolling back through the per-table Query C output — which for a multi-select run is hundreds of lines up. The confirmation now renders a table of ref / rows / size / DATA UPDATED, harvested from the Query C result that was already being fetched (no extra queries). DATA UPDATED is `storage_last_modified_time` rather than the metadata timestamp, since "when was this data last written" is the question that decides whether a table is dead. Column widths are fixed at 42/7/8/16 so the worst-case row is 79 display columns: a ref longer than 42 chars is middle-elided (head and tail both kept — the tail carries the table name, the head the project) and the full unelided refs are listed underneath whenever any elision happened, because a delete decision should never rest on a truncated name. The padded field is the *uncolored* ref, since `printf` pads by byte count and the ANSI sequences in the colored form would be counted as width and misalign every later column.

- `rlm-bq-archive` (`bq-archive`): **destinations are probed before the confirmation prompt.** `bq cp --no_clobber` already refused to overwrite, but it reported that per-table midway through the copy loop — after `yes` had been typed — so a run against a partially-archived selection read as "3 of 5 copies mysteriously failed". A parallel `bq show` fan-out now classifies every destination up front; existing ones are listed in red, excluded from the copy, and their sources never reach the delete stage. When every destination already exists the function returns before prompting at all.

- `rlm-bq-archive` (`bq-archive`): **post-copy verification, and it gates deletion.** Each copy is now checked with `SELECT COUNT(*)` on both source and archive; the counts must match for that table to be offered for deletion. `TABLE_STORAGE` logical bytes are compared too but are deliberately **advisory only** — storage stats lag writes by minutes, so a freshly-created destination legitimately reports 0 rows / 0 bytes and gating on it would block every delete on a fast run. The destination's `INFORMATION_SCHEMA` is addressed under `archive_proj`, not the source project or `BQ_ARCHIVE_QUERY_PROJECT`, which are not necessarily the same project. This replaces the previous verification, which was `bq-preview | head -10` on each side — human-readable but not an assertion, so nothing actually compared the two.

- `rlm-bq-archive` (`bq-archive`): **source tables can now be deleted from within the command**, one prompt at a time, and only where verification passed. Confirmation is the bare table name rather than `yes`: the prompts are near-identical and repeated once per table, which is exactly the shape that trains you to type the magic word without reading it, and the name has to be looked at to be typed. Confirming runs `bq rm --force --table` immediately. Deleted refs are appended to the shared `~/.cache/bq-open/dead-refs.txt` so the GC at the top of every `rlm-bq-*` invocation prunes them from the pickers and pooled history on the next run — otherwise the next `bq-archive` would keep offering tables that no longer exist. The generated `.sql` file now covers only sources still standing (declined, verification-blocked, or `bq rm` failed) and is skipped entirely when everything was deleted; emitting `DROP TABLE` for an already-dropped table leaves a file whose statements error out and obscure the ones that still matter. Exit status is non-zero when a copy failed, a destination already existed, or a confirmed delete failed.

- `rlm-bq-archive` (`bq-archive`): **selecting a view now offers to delete it instead of silently dropping it from the run.** A view stores no data — it is a saved SELECT — so `bq cp` has nothing to copy and an "archived" view would just be a detached duplicate of the definition. The previous behaviour recognised this but stopped there, printing a `bq show` / `bq rm` recipe and excluding the view; you then had to leave the tool and run those by hand. Since the reason you selected it is that you want it gone, VIEW and MATERIALIZED_VIEW entries now bypass diagnostics, confirmation, and copy, and are carried to the delete stage at the end where each is prompted for individually. There is no verification gate — nothing was copied, so there is nothing to compare — and the gate is instead the definition itself, printed in full immediately above the prompt so the one thing a drop destroys is in front of you when you decide. The definition is read from the JSON payload (`.view.query` / `.materializedView.query`) rather than bq's table rendering, which truncates long SQL to terminal width, and uses `--materialized_view` for materialized views since `--view` omits the definition for those. Nothing is written to disk: the DDL is shown, not saved. Deleted views join deleted tables in `dead-refs.txt` so they leave the pickers on the next `rlm-bq-*` run.

- `rlm-bq-archive`: **an aborted archive no longer strands selected views.** Carrying views to the end meant four early `return`s between classification and the delete stage — views-only selection, every destination already exists, copy declined at the prompt, nothing copied — each of which would have exited before the view prompts ran. They are now folded into an `archive_stage_ok` / `archive_rc` pair: the flag skips the remaining table-only stages while the run continues to the delete stage, and the return code those aborts used to produce is carried to the function's final exit status instead of being returned on the spot. Verified against all four shapes with a stubbed `bq`: a views-only selection reaches its prompts directly, and a mixed selection still reaches them after both the all-destinations-exist abort and a declined copy prompt.

### Fixed

- `rlm-bq-archive`: removed a duplicate `local _ref` declaration that printed `_ref=''` to **stdout** on every invocation. `_ref` was already declared for the in-scope cache scan, and the second bare `local` in the type-classification block is `typeset` in reporting mode. Pre-existing, but it only became visible once a run was exercised end-to-end with a stubbed `bq` — the stray line sits above the first real output, where it reads as noise from the cache helpers rather than from this function. Same gotcha as the two loop-body locals below.

- `rlm-bq-archive`: the two locals added inside the per-table diagnostics loop (`_c_line`, `_c_f`) carry explicit initializers. A bare `local x` in a loop body is `typeset` in *reporting* mode on every iteration after the first and prints `x=<value>` to **stdout** — reproduced here as two stray `_c_line=…` lines landing in the middle of the diagnostics output. See the "Bare `local x` inside a loop PRINTS" gotcha in `AGENTS.md`.

- `rlm-bq-archive`: the Query C harvest splits its tab-separated row with `"${(@s:<tab>:)line}"` rather than `IFS=$'\t' read`. `storage_last_modified_time`, `total_logical_bytes`, and `total_rows` are all NULL for external and snapshot sources, and `read` collapses a run of delimiters — with three leading empty fields it would have shifted `creation_time` into the `rows` slot, so an EXTERNAL table would have reported a timestamp as its row count in the confirmation table. Verified against a fixture with exactly that shape.

## [2026-08-05]

### Changed

- `rlm-fe` (`fe`): the picker now shows a keybinding header (`TAB multi • Enter open • Shift/Alt-↑↓ scroll • Ctrl-P size • Ctrl-G abort`), matching the `--header` convention already used by `rlm-dbt-ls`, `rlm-bq-open`, and `rlm-gar-open`. Kept to 73 display columns so it does not wrap at 80 — the first drafts ran 88-99 columns, and a wrapped header eats a second row of an already-short picker.

- `rlm-fe` (`fe`): **preview-pane scrolling is now bound and advertised.** `shift-up`/`shift-down` (one line) are fzf's own defaults but were undocumented, so nothing told you the pane could scroll at all; they are now bound explicitly, so the header cannot drift from actual behaviour if a future fzf changes its defaults. `alt-up`/`alt-down` are added for half-page jumps, since a source file is routinely longer than a 40%-height pane and line-at-a-time is not a practical way to reach the middle of one. Ctrl-U/Ctrl-D were considered and rejected: fzf binds them to `unix-line-discard` and `delete-char/eof` on the query line, and silently taking those away to gain a scroll key is a bad trade. No other picker in this repo binds preview scrolling; if that changes, these four are the shape to copy.

- `rlm-fe` (`fe`): entries are now ordered on a **single timeline**, newest first, with a humanized age ("2 hours ago") as the first column. A file's change time is its **filesystem mtime when git reports it dirty** (modified, staged, or untracked) and its **git last-commit time** when it is clean; files outside git keep the mtime. That is then `max()`'d with the MRU pick time. The dirty/clean split is the whole point: in a fresh clone every file's mtime is the *checkout* timestamp rather than an edit time — 500 sampled files in the `storytelhomepage` checkout share just **2 distinct mtimes** — so sorting on mtime, or on `max(mtime, commit_time)`, stamps the entire tree with one meaningless value and destroys the ordering it was supposed to produce. mtime only means "someone edited this" when git says the file is dirty, which is exactly when it should outrank the commit time. Visible effect in that repo: ages now spread across months / 1 year / years instead of a uniform "months ago". Dirty state costs one `git status --porcelain -z` per run (~0.03s here, ~0.15s in the partial clone). A clean file whose mtime was bumped by an unrelated tool — `.gitignore` right after a formatter run — now correctly reports its real age (13 days) instead of 9 minutes. Previously the picker pinned every previously-picked file above every unpicked one and sorted only the tail by mtime, which does not survive contact with the MRU cap: the history holds 500 entries, so in this repo (580 files) the pinned block was 500 rows and the mtime sort applied to the remaining 80 — the ordering was effectively "everything you have ever opened, in pick order". Folding the pick time into the same `max()` keeps the useful half of that behaviour (opening a file counts as touching it, so it floats to the top) while letting it decay, and it makes the visible order match the visible age column, which the pinned-block design could not do. The `picked_at` epoch is retained as field 1 of each row so callers can still distinguish picked entries.

- `rlm-fe`: git commit times come from one `git log --name-only` walk that resolves every tracked file in a single process, rather than a `git log -1` per file. **The walk runs with `GIT_NO_LAZY_FETCH=1`, which is a correctness requirement rather than a tuning knob.** In a partial clone (`--filter=blob:none`) walking history makes git lazily fetch missing objects over the network one round-trip at a time: the walk that costs 0.13s in this repo and 0.19s in a 16k-commit checkout hung for **over three minutes** in the `storytelhomepage` checkout, which is such a clone. The cliff is not commit count — 300 commits took 0.06s there and 1500 took 45s, because the cost is per missing object, not per commit. With lazy fetch refused git aborts at the first missing object in 1.16s, having still resolved ~78% of tracked files (2701 of 3484); the remainder fall back to filesystem mtime, which for a fresh checkout is within minutes of the commit time anyway. End-to-end `fe` in that repo now returns in 1.6s. Outside a git repo the step is skipped entirely, and git paths (which are relative to the repo root) are prefixed with `git rev-parse --show-toplevel` to match the absolute paths the picker keys on.

- `rlm-git-status` (`git-status`): status roll-up across every git repo in a directory, aimed at the multi-repo collection dirs `rlm-pr-worktree`'s multi-repo mode creates (one dir holding a worktree of every repo on a shared branch). The existing tools each answer a neighbouring question but not this one: `rlm-pr-list` reports where each repo's **PR** stands, and `wt-collection-preview` renders a change roll-up but only inside an fzf preview pane for a highlighted row — neither answers "what in this change set is still uncommitted or out of sync" from the shell, which is the question you have when picking work back up. The distinction is not academic — in the collection this was built against, all 7 members sit on a feature branch where one has a staged deletion and a *different* one is 1 commit behind `origin/main`; a single boolean would have shown two identical rows. Nothing is ever fetched, so divergence reflects the remote-tracking refs as they stand locally — the help file says so rather than implying freshness. - `rlm-afw-deploy` (`afw-deploy`): **waits for the deployed DAG code to actually become effective in Composer** instead of returning the moment the upload finishes. `afw sandbox deploy` ends at "the zip is in GCS"; the scheduler then picks it up on its own schedule, leaving a window where the deploy reports success but the *old* DAG code is still what runs. After a successful deploy the function now polls the environment's Airflow REST API until every deployed file has been re-parsed, printing a per-round progress line naming the files still stale and the time left. Skip with `AFW_NO_WAIT=1`; tune with `AFW_WAIT_TIMEOUT` (default 300s) / `AFW_WAIT_INTERVAL` (default 10s); the exit status is the wait's, so a timeout (2), an import error (3), or an unchanged upload (4) is visible to callers and to `$?`. **The design point worth remembering:** the obvious implementation — wait for `last_parsed_time` to exceed the upload time — does not work, and fails in the direction that matters. Composer re-parses the DAG bundle on a timer (~40-80s observed) whether or not anything changed, so that condition is satisfied by a periodic re-parse of the code already deployed; armed against an untouched environment it reported success in ~14s with nothing deployed at all. Clock skew is not the cause (client and Composer agreed to the second when measured) and the API exposes no content hash, so the check is anchored to the artifact instead: a pass requires the DAG zip's **GCS generation to have changed**, *and* the parse to be at/after the new zip's `updated` timestamp, *and* the parse time to differ from a snapshot taken before the deploy. The generation check is also what turns the wrong-bucket bug fixed below into an immediate, self-describing failure (rc 4, "the deployed zip in GCS did not change … check that afw is uploading to the bucket this environment actually reads") rather than a five-minute wait for a lie to come true. Success additionally reports `has_import_errors`, since "parsed" otherwise includes "parsed and failed to import" and would call a broken deploy clean. Verified against the live dev environment: rc 4 when nothing was uploaded, rc 0 after a real deploy whose parse (13:41:43) genuinely followed the upload (13:41:10).

- `_rlm-afw-wait-parsed`: new internal helper backing the deploy-wait step described in the `rlm-afw-deploy` entry above. Three modes: `snapshot` (emit `<relative_fileloc>\t<last_parsed_time>` per DAG for a pre-deploy baseline), `generation` (emit the DAG zip's current GCS generation), and the default poll loop. Talks to Airflow's `/api/v2/dags` — the Composer image is `composer-3-airflow-3.1.7-build.5` and Airflow 3 removed `/api/v1`, which now 404s with a JSON body pointing at v2. Auth is a plain `gcloud auth print-access-token`; an *identity* token (the usual reflex for an IAP-fronted service) gets a 401 from the Composer proxy — verified both ways. Matches DAGs on `relative_fileloc` (`<sandbox>_dags.zip/<file>.py`), which is derivable from the filenames the picker already has, and deliberately not on `dag_id`: the id carries a version suffix set inside the DAG body (`dbt_all_in_one_dag.py` → `ecerulm_dbt_all_in_one_v1.3`) and cannot be predicted from the filename. Handles token expiry mid-wait (401/403 → re-mint and continue rather than fail a 5-minute poll on a recoverable condition) and transient 5xx (retry, since the deploy itself already succeeded). Returns 0 parsed / 2 timeout / 3 parsed-but-import-errors / 4 zip generation unchanged / 130 interrupt; on timeout it says the upload succeeded and prints the Airflow URL, so the failure mode reads as "Composer is slow" rather than "your deploy broke". Two zsh/jq traps hit while building it, both silent: `jq --args` swallows every following argument as a positional, so the input JSON must be named as a file *before* `--args` — piping it in instead leaves jq waiting on a stdin it never reads and the call hangs forever (the response is written to a `mktemp` file, cleaned up via a function-scoped `TRAPEXIT`); and `$seen[] | select(...)` used as a generator emits **zero** rows when nothing matches, so the whole pipeline for that file produced no output and the `$hit == null` branch was unreachable — a DAG that never appears in the API was being silently treated as successfully deployed. `first($seen[] | select(...)) // null` collapses no-match to an explicit null. Both are covered by the fixture cases in the helper's own testing (missing DAG, parse before floor, parse after floor, baseline unchanged, baseline changed).

Because all seven members now land in scope, the collection also clears the `total >= on_disk` gate and gets its aggregate row, so it can be removed in one selection rather than seven. The two neighbouring cases are unaffected: inside a member worktree `--show-toplevel` resolves to the primary repo so single-repo mode still wins, and a dir that is neither repo nor collection still exits 1 (message now also mentions worktrees).
- `rlm-wts` (`wts`): collection mode worked from the *base* dir but died from inside a collection — the exact place you are standing when you want it. Run in `~/git/work/StorytelDataPlatform_20260729_DATA-2772-bigquery-import-lazy` it printed `wts: no collection directories matching StorytelDataPlatform_20260729_DATA-2772-bigquery-import-lazy_* in /Users/rubenlaguna/git/work` and returned 1. The glob was built from the cwd's **full** dirname, `${base:h}/${base:t}_*`, which only ever matches from the base dir: collections are leaves that hold repos, not further `<name>_*` children, so the pattern is guaranteed to match nothing one level down. The gate above it passed either way — a collection does contain git repos — so the function got far enough to fail rather than declining cleanly. `_rlm-wts-collections` now derives a **family stem** by truncating the dirname at the first `_` (`StorytelDataPlatform_20260729_DATA-2772-…` → `StorytelDataPlatform`) and globs `${base:h}/${stem}(N/) ${base:h}/${stem}_*(N/)`, so the base dir *and* every collection in the family are listed from any member of it — 12 entries here, identical whichever of the 12 you start from. The base dir is now a selectable row in its own right (previously unreachable from the picker, since it was only ever the implicit origin), and the cwd's row is flagged `<- here` so an unmarked no-op row isn't offered as a destination. Truncating at the first `_` is what makes both entry points collapse to one code path, and it degrades sanely: a dirname with no `_` is its own stem. The header now names the stem rather than the cwd. Two incidental hardenings while in there: the `<- here` marker is passed as a printf **argument** rather than interpolated into the format string (a collection dirname containing `%` would otherwise be read as a format specifier), and the marker uses ASCII `<-` after the `←` byte sequence proved awkward to round-trip through the row builder. Scope is unchanged for the two neighbouring cases — inside a member repo `git worktree list` returns 12 worktrees so normal mode still wins and collection mode is never reached, and in a dir that is neither a repo nor holds repos the gate still returns non-zero for the caller's silent no-op.

### Added

- `rlm-wts` (`wts`): **collection-directory mode**, reached automatically when the cwd is not inside a git repo. `rlm-pr-worktree`'s multi-repo mode (2026-07-24) turns a plain directory holding several repos — a *base* dir such as `~/git/work/StorytelDataPlatform`, which holds `data-platform-dbt`, `data-platform-infra`, … — into sibling *collection* dirs `<basename>_<YYYYMMDD>_<tail>`, each holding one worktree of every repo on a shared branch. Those sets were the one thing `wts` could not reach: its only data source is `git worktree list`, which in the base dir fails with `fatal: not a git repository`, leaving `paths` empty so the function hit `[[ ${#paths[@]} -eq 0 ]] && return 0` and returned **silently — no picker, no error, no hint that nine collections were sitting one directory up**. That empty-`paths` point is now a fork: the new inline `_rlm-wts-collections` globs `${base:h}/${base:t}_*(N/)` for sibling collections and, on success, cds into the pick; when the cwd is not a base dir it returns non-zero and the caller keeps the old silent no-op, so `cd /tmp && wts` behaves exactly as before. The `<basename>_*` glob is deliberate — collection dirs join with underscores while single-repo sibling worktrees use hyphens (`<repo>-<date>-<tail>`), so the pattern excludes the latter without a second test. It matches the dirname `_prwt_make_multi_worktree` generates by *default*, though, and that name is editable at the `vared` prompt, so a renamed collection will not be listed; the help file says so rather than pretending otherwise. The base-dir test is an inlined three-line "does any child answer `rev-parse --git-dir`" loop rather than a call to `rlm-pr-worktree`'s richer `_prwt_discover_repos`: that helper is defined *inside* the `rlm-pr-worktree` file and there is no `_prwt_*` autoload file, so `autoload -Uz _prwt_discover_repos` resolves to `function definition file not found` — it silently failed the gate and killed collection mode entirely during development. Only the boolean was needed anyway. Rows are **stat-only** (dirname, child count, mtime) and sorted newest-first via a zero-padded negated-mtime sort key in a hidden column; the tempting eager `git diff` sweep to show change counts up front was measured at ~1.7 s per collection, i.e. ~15 s before the picker would even appear for the nine collections here, so every git call was pushed into the preview, which fzf runs lazily for the highlighted row only. Jira keys embedded in the collection dirnames are pre-warmed into `~/.cache/wts-jira/` by the same parallel `_rlm-wts-jira-refresh` fan-out plus 3-second watchdog the worktree path already used (dirname only — reading a member branch would cost a git call per collection, and the preview does that fallback where it is already paying for git). Also silenced `git worktree list`'s stderr: outside a repo its `fatal:` line is not an error but precisely the signal to try collection mode, and it was leaking above the picker on every run.
- `wt-collection-preview` (new, `~/dotfiles/bin/`, auto-symlinked into `~/bin/` by `create_links_mac.sh`): the preview script for the above, the collection-level counterpart to `wt-preview`. It emits the Jira summary as an OSC 8 link (key taken from the dirname, falling back to a member's branch — `..._duplicates-ppb` and `..._replace-scd-macros-with-snapshots` carry no key in the name, and the line is omitted entirely when neither source yields one), the branch shared by the members (read from the first member that reports one; all members of a collection are on the same branch by construction), the collection's birthtime, the newest mtime across members, and a per-repo change roll-up. The roll-up shape was driven by measurement: in a real collection only 2 of 7 members differ from `origin/<default>`, so fanning out seven full `wt-preview` dumps would bury the two that matter. Instead each changed repo gets a header (`data-platform-infra  2 files  +17 / -8`) plus its `git diff --numstat` file list with aligned green/red counts — `--numstat` against the fork point, so uncommitted work counts too — while unchanged repos collapse onto one dim `unchanged: artifacts, contracts, dbt, looker, openmetadata` line. That line strips the longest `-`-delimited prefix shared by *every* member (`data-platform-`), computed across all members rather than just the unchanged ones so the abbreviation does not shift depending on which repos happen to have changes; a first cut used `${name%%-*}-` and produced the useless `platform-artifacts, platform-contracts, …`. The script carries its own `_wtc_link` / `_wtc_human_ago` / `_wtc_format_epoch` copies rather than sharing `wt-preview`'s, matching how each `bin/` preview script already stands alone — they run as separate processes and cannot autoload from `my-zsh-functions/`. Like `wt-preview` it never fails the picker: bad input, a dir with no worktrees, and a missing `acli` all exit 0 with the affected section omitted.

### Added

- `rlm-pr-checkout` (`pr-checkout`): new **inline** function (in `.zshrc`) that picks one of the current repo's open pull requests via fzf and switches to its branch in place. This fills a real gap between the two neighbours that each do almost-but-not-this: `rlm-switchbranch` lists local branches only with no PR context (so a PR you have not checked out yet is not even offered), and `rlm-pr-worktree` picks a PR but creates a *new* worktree rather than switching the current one. An explicit PR number skips the picker.
- `rlm-pr-checkout` (`pr-checkout`): **worktree-aware selection.** A branch can only be checked out in one worktree at a time, so a plain `git switch` to a branch some other worktree holds dies with `fatal: '<branch>' is already used by worktree at ...` (exit 128) — a real hazard here, where `rlm-pr-worktree` means most active PRs already *have* a worktree. The worktree you are currently standing in is deliberately excluded from that map (compared via `:A` to resolve symlinks), since switching to your own current branch is a no-op rather than a conflict and annotating it would be misleading. That `cd` is what forces the function to be inline in `.zshrc` rather than an autoloaded file, per AGENTS.md → Naming & Definition.
- `rlm-pr-list` (`pr-list`): new function listing the GitHub PRs for the branches currently checked out across a set of repos — the review status of a whole multi-repo change set in one table. Mode is auto-detected the same way as `rlm-pr-worktree` / `rlm-pr-worktree-rm-merged-closed`: inside a git repo it covers that worktree only; otherwise it discovers every git worktree sitting as a child of the cwd. The latter is the motivating case — `rlm-pr-worktree`'s multi-repo mode drops one worktree per repo into a single collection dir, all on the same branch (`~/git/work/StorytelDataPlatform_20260724_DATA-2769-foo/{data-platform-dbt,data-platform-infra,…}`), and until now checking "where is each of those PRs at" meant seven `gh pr view` calls by hand. Discovery deliberately does **not** reuse `_prwt_discover_repos`, which dedupes children to their main repo root via `--git-common-dir`; here the child worktree *is* the unit of interest, since it is its checked-out branch that identifies the PR. For each repo it resolves the PR whose head branch is that worktree's current branch (`gh pr list --head <branch> --state all`), so repos with no PR yet render as `no PR` — that absence is a feature, it names the repo still owing a PR. Columns are `REPO PR STATE CHECKS REVIEW UPDATED TITLE`: the PR number carries an OSC 8 hyperlink (padded *before* wrapping, since printf counts the zero-width escape bytes and would otherwise under-pad the column), STATE is colored per state, CHECKS collapses `statusCheckRollup` to `ok N` / `fail N/M` / `pend N/M` with SKIPPED and NEUTRAL excluded from the denominator, and UPDATED is a humanized age. Repos are queried in parallel (one backgrounded `gh` per repo writing a TSV line to a tmpdir), so the 7-repo collection above completes in ~1.1s rather than ~7×; the function `unsetopt monitor notify` first, since in an interactive shell that fan-out would otherwise print a `[4] 23959` / `[4]  + done …` pair per job above the table. `-i`/`--interactive` swaps the table for an fzf picker whose preview pane is `gh pr view`; ENTER opens the selection with `gh pr view --web`, and a no-PR row reports rather than opening anything.
- `rlm-pr-list` (`pr-list`): a **Slack-pasteable links block** after the table — bare `repo: url` lines, one per PR. - `rlm-pr-worktree-rm-merged-closed` (`pr-worktree-rm-merged-closed`): **collection aggregate rows** for the multi-repo worktree sets created by `rlm-pr-worktree`'s multi-repo mode. Every lookup therefore fell straight through to `man`. (Only `rlm-fcmd` ever worked, because it splits the list itself with `${(s.:.)HELPDIR}` and deliberately does not call `run-help`.) `.zshrc` now captures the stock function as `_rlm-run-help-orig` and defines a wrapper that walks the list the same way, trying the name as typed and then its alias expansion so both `run-help pr-list` and `run-help rlm-pr-list` resolve. (1) **jq `as` binds looser than `//`** — `.[0] // {} as $pr | rest` parses as `.[0] // ({} as $pr | rest)`, so jq short-circuits and emits the raw input whenever `.[0]` is truthy; the filter looks ignored and only misbehaves on non-empty data. Parenthesize `(.[0] // {}) as $pr`. (2) **`emulate -L zsh` turns EXTENDED_GLOB off** — every function here opens with `emulate -L zsh`, so `${var%%…##}` trims silently no-op; needs an explicit `setopt extended_glob`, and `%%[[:space:]]*` is not a substitute because `%%` is greedy from the left and eats the string. Older tickets remain findable via the JIRA web UI or by typing the KEY directly into `rlm-pr-worktree` / `rlm-jira-open`.

- `_rlm-jira-cache`, `_rlm-jira-history`, `_rlm-jira-sorted-rows`: picker is now sorted by a single composite key — `max(history_picked_at, updated_epoch, last_commented_epoch)` descending — instead of the old "history rows first, then the rest" interleave. A freshly-commented ticket can now outrank an old picked one; a never-picked-but-recently-updated ticket can outrank a picked-but-stale one; the 4-group priority survives only as a tiebreaker for the (extremely rare) case where two rows share a sort key. Implementation: (a) `items.tsv` grows from 5 fields to 7: `<group>\t<KEY>\t<status>\t<summary>\t<assignee>\t<updated_epoch>\t<last_commented_epoch>`, where the two trailing fields are integer Unix seconds populated by a new phase-B per-issue `acli jira workitem view --fields key,updated,comment --json` fetch — acli rejects those fields in the bulk-search `--fields` flag with "Error: fields 'updated, comment' are not allowed", so per-issue follow-ups are the only way to obtain them; parallelized via `xargs -P20`, each worker writes its raw JSON to `$tmp_views_dir/<KEY>.json`, then a single Python pass parses everything and merges with phase A's rows; measured ~5–8s for 50–80 issues against the real JIRA instance. (b) `history.txt` format becomes TSV `<epoch>\t<KEY>` so the sort can read `picked_at` per KEY; the legacy single-column format auto-upgrades on first read/append/migrate-legacy invocation via an in-place awk rewrite that assigns synthetic timestamps `now - rank * 60` (rank=0 for the bottom/newest line), preserving the existing MRU order exactly — atomic `mv` from a temp file, idempotent (a no-op if any line in the file already contains a tab). The `migrate-legacy` subcommand also runs the format-upgrade when copying from `~/.cache/jira-pick/history.txt`. (c) `_rlm-jira-sorted-rows` replaces its hand-rolled "history-first then cache" interleave with an inline Python composite-key sort that reads cache + history, builds `picked_at[KEY] = max(epoch)`, computes `sort_key = max(picked_at.get(key, 0), updated_epoch, last_commented_epoch)` per cache row, and emits in `(sort_key DESC, group_idx ASC)` order. (d) Per-group cap drops from 70 to 20 (so 4 × 20 = 80 raw rows before dedupe), which keeps phase B's per-issue fetch bounded at ~8s. (e) Both callers' parsers bump from `len(parts) < 5` / `NF>=5` to `< 7` / `NF>=7` to reflect the new row width; the renderers still use only fields 1–4 (display) and 1–5 (pr-worktree reshape), so the visible picker columns are unchanged.

### Fixed

- `rlm-pr-worktree`, `rlm-jira-pick`: silent exit immediately after picking an entry. Symptom: the picker rendered correctly, the user picked a row, control returned to the prompt — no vared prompt, no worktree, no error message. Root cause: the picker subshell `selection=$(... | column -t | fzf)` ran under the function-scope `set -o pipefail`. fzf stops reading from stdin once it has enough rows to render the first screenful; upstream `column -t` (and, in `rlm-jira-pick`, `_rlm-jira-sorted-rows`'s `cat` plus the inline `python3` renderer) then write into a paused pipe, eventually get SIGPIPE and exit 141. `pipefail` propagates that 141 out through the `$(...)` substitution, and the `|| return 130` immediately after the close-paren fires — silently exiting the function right after the user picked, before any vared prompt or worktree-creation logic could run. The bug was latent before the `_rlm-jira-cache` refactor because the old per-call `acli jira workitem search --limit 100` produced too few rows to trigger SIGPIPE in practice; the shared cache (even capped at 70 per group) is wide enough that the SIGPIPE actually fires. Fix: wrap each picker subshell with `setopt local_options no_pipefail` so pipefail is disabled only inside the subshell — the outer pipefail, which legitimately guards the jq pipelines that build `pr_rows` / `other_pr_rows` / `jira_rows` upstream in `rlm-pr-worktree`, stays in effect. A multi-paragraph header comment above the affected `selection=$(` in each file documents the SIGPIPE chain so a future edit doesn't reintroduce the bug.
